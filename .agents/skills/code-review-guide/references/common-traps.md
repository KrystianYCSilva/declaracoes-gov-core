# Common Code Review Traps (AI-Generated Code)

## Trap 1: Trusting Compilability as Correctness

**Symptom:** Code compiles and tests pass, but the implementation doesn't match the requirement. Agent wrote working code for the WRONG behavior.

**Cause:** LLM optimized for "make the test pass" not "solve the business problem." Tests may be testing the wrong thing.

**Fix:**
- In Pass 1 (Correctness), always check the REQUIREMENT first, then the code
- Verify test names match the requirement: `shouldCalculateDiscountForStudents` must actually test student discounts
- If the test was generated by the same agent as the code, review both with extra skepticism

---

## Trap 2: Invisible Dependencies

**Symptom:** Code works locally but fails in CI/production. Agent used a library feature that requires a version not in the project's POM/package.json.

**Cause:** LLM uses APIs from its training data which may be from a different version than the project uses.

**Fix:**
- Check ALL import statements against the project's declared dependencies
- Verify method signatures exist in the DECLARED version (not latest)
- Run `mvn dependency:tree` / `npm ls` and check for undeclared transitive dependencies

---

## Trap 3: Tutorial-Quality Code in Production

**Symptom:** Code looks like a Spring Boot tutorial — proper annotations, clean structure, but missing production concerns: logging, error handling, input validation, edge cases.

**Cause:** LLM training data is heavy on tutorials that demonstrate the "happy path" and skip production hardening.

**Fix:**
- Check for: logging, error handling, input validation, null checks, timeout handling
- If a method calls an external service without try/catch, flag as 🟡 Important
- If user input reaches a database query unsanitized, flag as 🔴 Critical

---

## Trap 4: Phantom Tests

**Symptom:** Test count looks impressive (50 tests!) but many tests assert trivial things: `assertNotNull(new User())`, `assertTrue(true)`, `assertEquals("test", "test")`.

**Cause:** LLM was told to achieve X% coverage and generated tests that execute code paths without verifying behavior.

**Fix:**
- Every test must assert at least one BUSINESS value (not just null/not-null)
- Look for assertions that are tautologies (`assertTrue(true)`, `assertEquals(x, x)`)
- Check that test setup is non-trivial (tests with empty setup usually test nothing)
- Mutation testing reveals phantom tests: if you change production code and no test breaks, the tests are useless

---

## Trap 5: Confident but Wrong Error Messages

**Symptom:** Error messages in catch blocks don't match the actual error condition. "User not found" when the actual error is a database connection failure.

**Cause:** LLM generates plausible error messages from context, not from the actual exception semantics.

**Fix:**
- Every catch block must log or re-throw with information from the caught exception
- Error messages must include the discriminating data (which user ID? which query? which table?)
- Generic messages like "An error occurred" are always 🟡 Important
